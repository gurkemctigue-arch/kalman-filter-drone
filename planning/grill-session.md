# 毕业设计计划书规划会话

## Request

在正式进入设计前，审查并重构“基于 YOLO 与卡尔曼滤波的无人机视觉目标跟踪及自主跟随系统”计划，随后生成可执行的最终版计划书。

## Map

### Goal

- 先完成仿真系统设计，再决定是否扩展到实机。
- 覆盖行人与车辆两类目标。
- 支持单实例场景，以及多个同类目标中持续跟随指定个体的场景。
- 相机安装在云台上，但云台不是硬性验收项。
- 不依赖师兄现有 ROS1 工程；技术栈由本项目独立选择。

### Current plan

初步链路为 YOLO 检测、RGB-D 三维定位、卡尔曼滤波、PID 跟随和短时丢失处理。原计划尚未定义身份关联、坐标系、时间同步、控制接口、实验统计和里程碑。

## Unknowns ledger

### Known knowns

- 目标平台：仿真优先。
- 目标类别：行人和车辆。
- 相机：安装在云台上。
- 云台：不是硬性验收项。
- 不受师兄 ROS1 工程约束。
- 需要考虑唯一目标与多同类目标中的指定个体两种模式。
- 用户希望两类目标和两种身份模式都纳入设计；将采用分层验收，不把所有扩展同时作为首轮闭环门槛。
- 当前开发主机为 Windows，WSL 实际发行版为 Ubuntu 24.04.1；ROS/Gazebo/PX4 的安装状态以本次联调记录为准。

### Known unknowns

- “指定个体”如何初始化：用户选框/指定 ID，还是仅按类别自动选择。
- 多目标模式是否要求遮挡后保持身份，还是只要求短时无遮挡关联。
- 采用哪一套 ROS 2、PX4、Gazebo 版本组合。
- 研究主贡献放在状态估计、身份关联，还是完整系统集成。
- 云台在第一阶段是锁定、只仿真关节，还是加入视线控制实验。
- 是否接受按“核心闭环、指定个体扩展、主动云台扩展”分层设定验收标准。

### Unknown knowns

- 用户可能希望“后续可移植”但尚未指定目标实机；需要用参数化模型和稳定接口表达这一标准。
- 用户可能把“检测到同类目标”与“持续跟踪指定个体”视为同一件事，需要先建立术语边界。

### Suspected unknown unknowns

- 云台运动会使相机外参随时间变化，直接在相机坐标系做 KF 会失效；风险高，需用带时间戳的 TF 和稳定世界坐标系验证。
- RGB-D 深度、PX4 位姿、检测结果的时延和坐标变换会主导闭环性能；风险高，需在仿真中显式注入噪声与延迟。
- 多目标模式若引入完整 ReID，工作量会超过本科项目；风险高，需先定义“用户初始化 + 运动/外观关联”的最小问题。

## Domain model

| Term | Meaning | Avoid | Evidence / Source |
| --- | --- | --- | --- |
| 单实例模式 | 场景中只有一个可跟随的目标实例；不要求解决同类身份歧义 | “单目标跟踪”等含混表述 | 当前讨论 |
| 指定个体模式 | 初始时选定一个具体实例，后续在同类检测中保持其身份 | 将“同一类别”误写成“同一个体” | 当前讨论 |
| 检测 | YOLO 在单帧输出候选框、类别和置信度 | 把 YOLO 本身称为跟踪器 | YOLO 工作方式 |
| 状态估计 | 由测量估计位置、速度并在短时缺测时外推 | 宣称 KF 能完成重捕获 | 视觉/控制审查 |
| 可移植性 | 算法节点不绑定某个真实硬件，通过标准话题、TF、参数和仿真模型替换传感器/飞控 | “仿真一次即可直接上任意无人机” | 系统设计原则 |

## Design tree

### Branch: 目标身份

- Decision: 待确认，建议把两种模式做成同一管线的两个配置档。
- Options: 单实例；用户初始化的指定个体；自动语义指定/ReID。
- Recommended answer: 单实例为 MVP；用户框选/指定检测框的指定个体为扩展；暂不承诺自然语言属性检索或完整 ReID。
- Status: assumed pending user confirmation

### Branch: 仿真硬件

- Decision: 不要求现在知道最终实机型号，但必须选一个参考配置并参数化。
- Options: 完全抽象；固定参考无人机/相机/云台模型；直接绑定未来实机。
- Recommended answer: 固定一套参考仿真配置，同时把内参、噪声、延迟、视场、云台限位、动力学和话题接口全部参数化。
- Status: assumed

### Branch: 交付分层

- Decision: 用户希望行人、车辆、唯一实例和指定个体都覆盖，但主动云台不硬性验收。
- Options: 所有组合一次性做完整闭环；核心闭环与身份/云台扩展分层。
- Recommended answer: 两类目标都做唯一实例闭环；指定个体先做同一管线的多目标关联与短遮挡验收，再择一类做更完整闭环；主动云台最后接入，锁定云台仍保留标准接口。
- Status: assumed pending user confirmation

## One-question-at-a-time grill queue

1. 在多同类场景中，是否接受“开始时由用户/测试脚本选定目标框，系统随后负责保持该个体身份”作为指定个体的定义？
   - Why it matters: 若要求系统自动理解“跟踪穿红衣的人”，需要额外的 ReID/属性识别，架构和工作量会显著扩大。
   - Recommended answer: 接受用户初始化；这是可复现且适合本科项目的定义。

## Resolved assumptions

- 首版只做仿真，实机迁移不是当前验收项。
- 云台控制先作为可插拔模块，不阻塞固定相机/锁定云台下的主线验证。
- 不依赖实验室遗留 ROS1 代码。
